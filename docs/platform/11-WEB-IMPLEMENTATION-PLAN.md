## 1. النتيجة الحاسمة للتدقيق: القلب قابل للمشاركة فعلاً

قبل اختيار أي إطار، كان السؤال الوحيد المهم: **هل يمكن للويب أن يستهلك القلب
نفسه، أم سيُضطر إلى نسخه؟** فُحص هذا فعلياً لا افتراضاً:

```
src/data/     يستورد فقط من:  src/data/**  و  src/platform/**
src/platform/ يستورد:          لا شيء إطلاقاً (صفر استيراد)

استيراد React داخل src/data/          →  لا شيء
استيراد src/components أو src/views   →  لا شيء
استيراد src/lib/firebase              →  لا شيء
لمس document/window/localStorage      →  لا شيء (الإشارتان الوحيدتان نصّ في تعليق)
```

`src/platform/storage.ts` هو النقطة الوحيدة التي تلمس `localStorage`، وهي
**آمنة أصلاً للتصيير على الخادم**: `readRaw`/`writeRaw` ملفوفتان في `try/catch`،
فغياب `localStorage` يُعيد `null` بدل أن يرمي.

**الأثر:** الويب يستورد القلب حرفياً عبر Path Alias. **لا نسخ، ولا نقل ملفات،
ولا تعديل على شيفرة الهاتف.** هذا وحده يُلغي أكبر خطر في الطلب — التكرار.

## 2. المعمارية المختارة: Next.js 16 (App Router) داخل `web/`

### لماذا لا Vite SPA كالتطبيق

الطلب صريح: «لا تجعل جميع الصفحات Client-only إذا كان المحتوى العام يحتاج SEO».
موسوعة عربية غير مفهرسة تفقد سبب وجودها. وVite SPA لا يصيّر على الخادم.

### لماذا لا Astro

ممتاز للمحتوى، لكن نصف المنصة تطبيقيّ الطابع: مساحة المشروع، لوحة الإدارة،
المجتمع التفاعلي. سنقاتل الإطار في نصف الصفحات.

### لماذا Next.js

| المتطلب | كيف يلبّيه |
|---|---|
| SEO للمحتوى العام | Server Components + `generateStaticParams` → HTML كامل مفهرس |
| Firebase Admin على الخادم فقط | Route Handlers / Server Actions — الحزمة لا تصل المتصفح أبداً |
| حماية `/admin` قبل التصيير | Middleware + تحقق خادمي، لا إخفاء أزرار |
| تقسيم الحزم | تلقائي لكل مسار |
| TypeScript / RTL | مدعومان مباشرةً (`<html lang="ar" dir="rtl">`) |
| القلب المشترك | Path alias إلى `../src/**` — بلا نسخ |

**النسخة:** Next 16.2.12، React 19 (نفس نسخة التطبيق — لا ازدواج).

### لماذا `web/` كمجلد منفصل وليس دمجاً

قرار مقصود لتقليل المخاطر إلى الصفر:

- **لا ملف واحد من التطبيق يتحرك.** `vite build` و`cap sync` و57 حزمة كسولة
  و7,509 تأكيداً تبقى كما هي حرفياً.
- بناءان مستقلان: `npm run build` للهاتف، `npm --prefix web run build` للويب.
- القلب مشترك بالاستيراد لا بالنسخ، فأي تعديل عليه يصل الاثنين فوراً — وبوابات
  الهاتف تحرسه.

```
fpv-arabic-app/
├── src/            ← تطبيق الهاتف (Vite) — لم يُمَسّ
│   ├── data/       ← القلب المشترك ─────────┐
│   └── platform/   ← العقود المشتركة ───────┤
├── web/                                     │
│   ├── app/        ← مسارات Next            │ استيراد
│   ├── lib/        ← محوّلات الويب           │ (لا نسخ)
│   └── tsconfig.json  @core/* → ../src/* ◄──┘
├── functions/      ← Cloud Functions — لم تُمَسّ
├── firestore.rules ← تُمدَّد، لا تُستبدَل
└── storage.rules   ← تُمدَّد، لا تُستبدَل
```

### ب. يحتاج Adapter للويب

| الجزء | لماذا | الحل |
|---|---|---|
| الوجهات → روابط | `resolveDestination` يُنتج مسارات التطبيق | `web/lib/webRoutes.ts` — محوّل **واحد**، لا مسارات يدوية في المكوّنات |

### ج. يحتاج واجهة ويب جديدة (عرض فقط — لا منطق)

الصفحة الرئيسية، هيكل متعدّد الأعمدة، فهرس المقال الجانبي، جداول عريضة،
لوحة الإدارة، مركّب المجتمع الأوسع. **لا منطق أعمال داخل أي منها.**

### د. يحتاج منطق خادم (جديد)

| الجزء | لماذا |
|---|---|
| `web/lib/server/firebaseAdmin.ts` | Admin SDK — خادم فقط، أبداً في المتصفح |
| `web/lib/server/requireRole.ts` | التحقق من الدور من مصدر موثوق |
| `web/app/api/admin/**` | عمليات الإدارة، كلٌّ يتحقّق من الدور قبل أي فعل |
| `web/middleware.ts` | يمنع `/admin` قبل التصيير |
| أداة منح الدور | نص خادمي (لا واجهة) لمنح أول مالك |

### هـ. يحتاج مراجعة أمنية

| البند | الحالة |
|---|---|
| الأدوار | اليوم `'user' \| 'moderator'` فقط في `src/components/Community/types.ts` — تُمدَّد إلى ستة |
| مصدر الدور | اليوم `users/{uid}.role` في Firestore، «console-only» بلا مسار كتابة للعميل |
| رفع الصور | `storage.rules` محصّن أصلاً: مسار مملوك، قائمة MIME، سقف 2MB، نمط اسم |
| الفيديو | `MediaType` يحوي `'video'` في المخطط، وغير مفعَّل في الرفع |
| سجلّ التدقيق | **غير موجود** — يُنشأ |

### و. يحتاج ترحيل بيانات

**لا شيء في المرحلة الأولى.** توسيع `UserRole` إضافي بحت: كل مستخدم قائم `'user'`
أو `'moderator'` ويبقى صالحاً. أي وثيقة بلا حقل جديد تُقرأ بقيمة افتراضية.

### ز. يؤجَّل

البوت، المزامنة الشاملة، محرّر Wiring، تحويل الفيديو الاحترافي، إدارة موسوعية
كاملة، التعاون الحي، الدفع.

## 4. الأدوار — التوسيع لا الاستبدال

اليوم دوران: `user`, `moderator`. المطلوب ستة. القاعدة الحاكمة: **`moderator`
يبقى بمعناه وصلاحياته الحالية** حتى لا تنكسر قواعد Firestore القائمة التي
تستدعي `isModerator()` في مواضع كثيرة.

| الدور | المعنى |
|---|---|
| `user` | الافتراضي |
| `moderator` | مشرف مجتمع — **موجود، لا يتغير** |
| `reviewer` | مراجع محتوى — قراءة الإدارة، لا تعديل |
| `editor` | محرر — محتوى تعليمي، لا مستخدمين |
| `admin` | مدير — مستخدمون ومحتوى، لا يمسّ المالك |
| `owner` | مالك المنصة — لا يُحذف ولا يُخفَّض |

**مبدأ أقل صلاحية:** كل قدرة تُمنح صراحةً لكل دور، لا بالوراثة الضمنية.

**كيف يُمنح أول مالك:** أداة خادمية تُشغَّل يدوياً بـUID، تكتب الدور بـAdmin SDK.
**لا بريد ولا UID داخل حزمة العميل.** حتى تُزوَّد بالبيانات، لا يملك أحد `owner`
— وهذا هو السلوك الآمن.

**التحقق طبقتان:** Custom Claims (سريع، بلا قراءة) + وثيقة Firestore (مصدر
الحقيقة للقواعد). العميل لا يُصدَّق أبداً.
